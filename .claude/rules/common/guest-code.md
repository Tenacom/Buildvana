# Guest code

This file is the same in every repository that copies `.claude`. A fact specific to one repository lives in another rule file.

Guest code is code that a package adds to a project that references it. The output of a source generator is guest code. So is a source file that a package adds to the project as a `Compile` item.

The analyzers, the coverage collector, the code metrics, and the debugger of that project take guest code for code of the project, unless the code says otherwise. [Well-behaved guest code](https://riccar.do/posts/2022/2022-05-30-well-behaved-guest-code.html) describes what each tool reads. The rules below make every one of them leave guest code alone.

## The file

- The name of a guest file ends with `.g.cs`. For a source generator, the name is the hint name it passes to `AddSource`.
- A guest file starts with the comment below, where `<package>` is the id of the package that the code comes from.

  ```csharp
  // <auto-generated>
  // This file was automatically generated by <package>. DO NOT MODIFY!
  // </auto-generated>
  ```

- In a file that no tool generates, the second line is `// This file is part of <package>. DO NOT MODIFY!`.
- A blank line and `#nullable enable` follow the comment. The compiler turns the nullable context off in a file it takes for generated code, as [Nullable](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-options/language#nullable) says.

The compiler takes a file for generated code on either sign, and then reports no analyzer diagnostic in it. A file needs both signs. The compiler may change a hint name, and a coverage tool that excludes files by name cannot read a comment.

## Types and members

- A guest type has the three attributes below.
- A member that guest code adds to a type of the project has the three attributes itself. An attribute on a partial type applies to the whole type, the part of the project included.
- The arguments of `GeneratedCode` are the id and the version of the package.
- Write each attribute with its full name after `global::`, because guest code cannot rely on a `using` directive or on the namespace it sits in.
- Never write `CompilerGenerated` in guest code. The attribute is for the code that the compiler itself generates.

```csharp
[global::System.Diagnostics.DebuggerNonUserCodeAttribute]
[global::System.Diagnostics.CodeAnalysis.ExcludeFromCodeCoverageAttribute]
[global::System.CodeDom.Compiler.GeneratedCodeAttribute("<package>", "<version>")]
```

`DebuggerNonUserCode` keeps the debugger from stepping into the code. `ExcludeFromCodeCoverage` is the one mark that coverage tools of every vendor honor. `GeneratedCode` takes a type out of the code metrics, and makes the analyzers treat a member as generated code.

`ExcludeFromCodeCoverage` on guest code has no `Justification`, which older frameworks lack. This is the one exception to "Coverage exclusion policy" in `testing.md`. The tests of the package cover the guest code, in the test project of the generator.

## The version

A generator takes the version of its package from `ThisAssembly.AssemblyInformationalVersion`. Buildvana SDK generates the `ThisAssembly` class in every versioned C# project. Do not read `AssemblyInformationalVersionAttribute` through reflection.
